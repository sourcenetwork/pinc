# Proofs

`proofs/tla/` and `proofs/lean/` hold TLA+ specifications, checked with TLC, and Lean 4 proofs of VINC's state machines
and pure functions. Both are kept identical to the Rust code by validating traces recorded from the real code against
each. Proven in full: `vinc-wire`, `vinc-dag`, `vinc-crypto`, `vinc-keystore`, `vinc-security` (handshake, key schedule, record keys, key roll, credit
record, amplification budget and padding, ticket stores, prekey cache), `vinc-values`, `vinc-dtn` (custody, the charged
store, forwarding, erasure coding, layout, codecs, reception, one-shot encryption and the multi-node scenarios) and the
relay side of `vinc-connect` with its codecs, carrier link and client rules. `vinc-membership`, `vinc-broadcast` and `vinc-reconcile` are proven except for the
items under [Being closed](#being-closed).
Run everything with `just proofs`.

## How it is checked

By `scripts/proofs.sh` (the `== proofs` step of `scripts/gate.sh`):
- **Lean** (`proofs/lean`, a Lake package on core Lean and Std, no Mathlib): `lake build` checks every proof. A script
  rejects `sorry`, `admit`, `axiom` and `native_decide` in the sources, and the build fails if any declaration of the
  package depends on an axiom beyond `propext`, `Classical.choice` and `Quot.sound` (`#audit_package`, plus a
  printed `#audit_axioms` line for every main theorem).
- **TLC** model checks every TLA+ config in `proofs/tla` over the bounds in the table. TLC integers are 32 bits wide,
  so the specifications of the machine-integer code (`Varint`, `Layout`, `Encoder`, `BuilderBytes`, `VerifierBytes`)
  write every `u64` and `usize` as a word of five 16-bit limbs (`U64.tla`). Each operation of the Rust code has an
  operator with the semantics of the code: a plain `+`, `-`, `*`, `<<`, `>>`, `/` or `%` that overflows, underflows,
  shifts by 64 or more or divides by zero, a `try_from` that does not fit where the code unwraps it, an `ilog2` of
  zero, a slot that is not found and a push onto a full stack all stop TLC with an error, so a model check that
  finishes has shown that none of them is reachable in the checked domain. `checked_*`, `saturating_*` and
  `try_from` return their option or saturate. The cases of these specifications are the states of a machine whose
  root has one successor per seed, so all workers generate and check cases at once; the byte-level specifications
  (`BuilderBytes`, `VerifierBytes`) are machines that feed pieces, so TLC explores every split.
- **The link between the two languages.** Each specification names, in its header, the Lean theorems it
  corresponds to, and the table below gives the specification and the theorem side by side. The boundary sets are the
  same on both sides: for every `j` in `0..64` the values `2^j - 1`, `2^j` and `2^j + 1`, the byte classes, the
  addends of `encoded_len`, the group buffer sizes, the shapes of the paths in a tree of `2^54` groups and the
  completed-group counts of the builder. `proofs/lean/Vinc/Link.lean` evaluates the Lean models of the code on
  those sets and the kernel checks the result (`decide +kernel`; the values below 16500 and the strings of 3 and 4
  bytes of `Varint.tla` are cut to 130 and 2 bytes, and the path and slot theorems take 16 values of `j` out of 55,
  `bigJ` in `Link.lean`, to keep the kernel's time within the budget), and the Rust traces of `tests/trace_tla.rs` run
  the real code on them for TLC. The Lean statements are general (`Varint.decode_encode` holds for every `v`); the TLA+
  checks are bounded; the sets are the place where the two meet, so a value accepted by one and refused by the other
  shows up in the build.
- **Trace validation.** The Rust tests `tests/trace_ranges.rs`, `tests/trace_verifier.rs` and `tests/trace_builder.rs`
  run seeded random sequences through the public API, compare every answer with a naive reference or with the genuine
  value, and, when `VINC_TRACE_DIR` is set, write them as ndjson. `trace_ranges` covers `VerifiedRanges<N>`,
  `VerifiedRangesVec`, `varint` and `Layout`: TLC checks that the recorded insert sequence is a behaviour of
  `VerifiedRanges.tla` (`TraceVerifiedRanges.tla`: every step is an `Insert` step with the run's capacity, and the
  recorded `covered_len`, `contains` and `contains_range` equal the specification's).
  `trace_verifier` runs the real `RangeVerifier` on genuine `encode_range` streams and on streams with a flipped bit,
  cut short or followed by extra bytes, fed in windows of every size (the whole stream, single bytes, item-sized,
  random), and records one event per `feed` call: the input length and its offset in the stream, what the verifier
  reported (consumed bytes, released offset, error, `next_len`, `is_complete`) and, when the call completed a stream
  item, the item, the offset of its first byte and the hash call the verifier made for it, with the chaining value the
  code computed for it (the oracle; chaining values and group bytes are ids). `TraceRangeVerifier.tla` (reusing
  `StepWith`, `QueryKey` and `Left` of `RangeVerifier.tla`) and `lake exe replay` (running the proved `Tree.feed` and the
  byte-level `VerifyBytes.feedCode`) check that the oracle is a function (one value per hash call) and that every
  decision is the model's under that oracle: the hash call is the one the model makes for the item, the item is accepted
  or rejected, the group released and the parents pushed as the model does, the error kind is right, a failed verifier
  repeats its error, and the stream steps of the public `RangeEncoder` name the model's nodes (a parent's outboard
  offset is 64 times its pre-order position). The same files carry the buffer: the replay runs the byte-level model on
  the real offsets (the input of a call is the bytes `pos .. pos + ilen` of the stream, the unconsumed tail is fed
  again, the model's buffer holds the offsets already taken), so the bytes consumed, `next_len`, the fast-path
  predicate (nothing buffered and the whole item in the input), the offset of the released group and the exact bytes of
  the item it holds equal the model's, and a released group borrows the input exactly on the fast path and the
  verifier's buffer otherwise (`ptr`, the one fact the value model cannot state); TLC checks that the offsets advance
  by the bytes consumed and that a completed item starts at `pos - filled`.
  `trace_verifier` also records the complete step list of the public `RangeEncoder` for layouts from one group to
  `2^54` groups (a value of `u64::MAX` bytes: the encoder needs only the layout), around every power of two and with
  ranges at the start, the end and in the middle, and `encode_range` into output buffers of every size around the
  stream's length. `lake exe replay` checks each step list against `Encode.encRun`, so the outboard offset of every
  parent step and the split of every node visited are the proved functions' (`left_groups`, the pre-order position),
  and each `encode_range` result against `Machine.encodeRangeM`.
  `trace_builder` runs the real `OutboardBuilder` on random values, group sizes (1 to 8 KiB, and 1 KiB groups up to
  150 groups) and splits of the value into pieces (whole, a few bytes, group-sized, one byte off a group, random), with
  the error cases between the real calls (a buffer of the wrong size, a piece past the declared length, `finish` before
  the last byte, a piece of 0 bytes, data after the end). A run starts with the genuine tree of the value, computed
  from the definition of the BLAKE3 tree with the BLAKE3 library, never by the code under test; each call is an event
  with the slots of the buffer that changed, found by comparing the buffer before and after. `TraceBuilder.tla` and the
  replay (running `BuilderBytes.updateCode` and `finishCode` under the recorded tables) check that the result of every
  call is the model's, that the slots written are exactly the model's, each at the pre-order position of its node
  (`Layout.preorderIndex` in Lean, `Pos` counted from the definition in TLA+) with the pair of genuine chaining values,
  and that the root `finish` returns is the genuine root; the root of the empty value must equal the recorded hash of
  the empty input, which the test takes from `blake3::hash(b"")` and the verifier's `RootMismatch` check uses.
  `trace_tla` runs the real `varint`, `Layout`, `RangeEncoder`, `encoded_len` and `encode_range` on the boundary
  sets the TLA+ models enumerate and on seeded random inputs, and writes every `u64` as four 16-bit limbs (TLC cannot
  read a number above 2^31 from JSON, it wraps it silently), to `tla/` under `VINC_TRACE_DIR`: `TraceVarint.tla`,
  `TraceLayout.tla` and `TraceEncoder.tla` check each recorded call against `Varint.tla`, `Layout.tla` and
  `Encoder.tla` (the same operators the model check runs). The builder trace is checked by `TraceBuilder.tla`, which
  runs the recorded calls through `BuilderBytes.tla` (`UpdateCall`, `FinishCall`) with the recorded hash tables as the
  hash, and `TraceRangeVerifier.tla` takes the buffer decisions (`Plan`, `NextLen`) from `VerifierBytes.tla`. The
  events of the pure functions are independent, so TLC checks them as separate states on all workers.
  `lake exe replay` also replays the ranges, varint, layout and size traces (`groups`, `depth`, `outboard_size`,
  `group_size` over lengths up to `u64::MAX` and every group log) against the Lean functions and fails on any
  difference.

Tools: Lean 4 and Lake, TLC on `PATH` as `tlc`, Java, and for the trace check a TLC of the same era as the
[CommunityModules](https://github.com/tlaplus/CommunityModules) jar (the gate prints the download command when a
jar is missing).

Every theorem named above has an `#audit_axioms` line, and `#audit_package` covers the rest. The handshake theorems are
over a free term algebra for the primitives and a Dolev-Yao attacker that owns the node `A`, drops, reorders,
duplicates, replays and injects every message it can build, and never learns an honest node's long-term or ephemeral
secrets. The Lean attacker is a superset of the TLA+ one, with any number of sessions, nodes and tickets and any ticket
store capacity. The TLA+ model is the bounded cross-check and the bridge to the code: `TraceHandshake.tla` and the Lean
replay run the recorded steps of the real state machines through the same step functions (`HsOps.tla`,
`HandshakeModel.lean`). The handshake models were mutated and TLC or the trace check fails on each: a Resumed amplification factor of 0, a changed
resend budget, the full prekey every second send instead of the third, the fallback on the second send, a client store
without per-peer replacement, a server victim that skips expired slots, a skipped binder check, a late context that is
not cleared by `shed`, a client `take` that ignores the ALPN, an export that returns the oldest tickets; and a changed
field of a recorded line (a message length, an event, a ticket id, a connection id secret, a flag) fails both TLC and
`lake exe replay`. The factor 3 of the resend rule becoming 4, and dropping the removal of an expired slot on a rejected
Hello, fail trace validation too: the traces record the bound the code computed for a repeated Reply and the ticket
slot table of the responder after every step with its clock. Swapping two absorbs of any transcript fails
`TraceTranscript.tla` and the replay. A TLC config of the key roll with the answer not naming its request, one with the
duplicate dropped by the gate and one with the orphaned staged key are kept as witnesses that the three findings are real.

TLC bounds of the handshake (`Handshake.cfg` and three more; each is a separate model; the script runs up to three models at a time):
- `Handshake`: one initiator at node 1, one responder at node 2, the attacker node, the short Initial allowed, every
  forged Initial, Hello and Reply the attacker can build: 27592 distinct states.
- `Handshake_resume`: a seeded ticket, one initiator, two responder sessions of one node (the replay): 49048 states.
- `Handshake_late`: the loss timers fire (the third-send fallback, late resume replies, repeated Hellos and Initials
  answered by a resumed responder, `shed`): 240672 states.
- `Handshake_stores`: two initiator and two responder sessions, ticket ids drawn from a pool of two so they can collide,
  the client store accepting tickets and exporting, restoring and restarting: 15532 states.
The forged messages of the last three configs are only those the property needs (a bad binder, copied connection ids, a
forged late reply); the full attacker is in `Handshake`, and the Lean attacker, which sends any message it can build, is
a superset of all four.

## Assumptions

The only things taken on trust are the dependencies, not this repository's code:
- The cryptographic primitives behave as specified: BLAKE3 is collision resistant and a PRF (the transcript hash, the
  key derivation and the binder tags), X25519 and ML-KEM-768 give shared secrets only the key holders know, the AEADs
  (ChaCha20-Poly1305, AES-128-GCM) are ideal authenticated encryption, the signature algorithms are unforgeable. These
  appear as the free term algebra and the Dolev-Yao `Known` predicate in the handshake model, as `HashInj` and
  `IdealAead` hypotheses in Lean, and as `Tree.CollisionFree` for the verifier.
- The packet key is an injective function of the traffic secret (a property of the key derivation `expand`; a hypothesis
  of `Record.no_nonce_reuse` and `KeyRoll`), and X25519 gives the same shared value to both sides.
- Rust `core` and `std` semantics, each stated as a hypothesis of the theorems that use it, never as an axiom:
  - the integer operations (`checked_*`, `saturating_*`, shifts, `/`, `%`, `div_ceil`, `is_multiple_of`,
    `try_from`, `is_power_of_two`) mean what their documentation says; `Machine.lean` defines them that way;
  - `u64::leading_zeros(x)` for `x != 0` returns the `z` with `2^(63 - z) <= x < 2^(64 - z)` (`Layout.IsLz`, the
    hypothesis `hlz` of `Layout.depth_eq` and `Machine.depthM_eq`);
  - `u64::ilog2(x)` for `x != 0` returns the `z` with `2^z <= x < 2^(z + 1)`, and `usize::trailing_zeros(2^k)` is `k`
    (`Machine.IsIlog2`, the hypotheses `hil` and `htz` of `Machine.leftGroupsM_eq` and `forGroupBytesM_iff`);
  - slice `get`, `split_at_checked`, `copy_from_slice` and `partition_point`, and the
    `#![forbid(unsafe_code)]` guarantee.
- BLAKE3 as the tree code uses it, beyond collision resistance: hashing a group in several `update` calls gives the
  hash of the concatenation, and `set_input_offset`, `finalize`, `finalize_non_root` and the two `merge_subtrees`
  functions compute the abstract `leaf` and `parent` values of `Tree.Hash`, with the group offset and root flag the
  model passes. The proofs do not check this; the traces do, on real data.
- The libraries below `vinc-crypto` and `vinc-keystore` answer as specified, each an abstract function in the model with
  the code's use of its answer proved: the signature crates (does a key parse, does a signature parse, is `s` low, does
  the equation hold: `Prim`), the `ChaCha20` stream and the AES block (`StreamInj` where a theorem needs the output to
  determine the key), ChaCha20-Poly1305 as an ideal AEAD (`Ideal`, `AeadSpec`), `tpm2-protocol` (its verdict on a body
  and on the public area of a blob), the operating system's random source, and the TPM (a software TPM in the traces).
  The transport of the TPM client pairs each command with its own response; the response carries no command code, so the
  client cannot check it.

## Being closed

These items are still open; they are listed so nothing is hidden:
- `vinc-crypto` and `vinc-keystore`: the labels of `vinc-broadcast` are private constants, so they are not in the label registry or its trace; the zeroization statement covers the named buffers of the crate, not the copies a dependency makes of a scalar passed by value; the TPM store is traced against a software TPM only, and a refused flush after a failed `ReadPublic` in `generate` leaks the handle without an error; the TPM refuses an object auth value longer than the digest of its name algorithm (32 bytes), which the client reports as the TPM's code. The TPM client's resend of a command answered `TPM_RC_RETRY`, `TPM_RC_YIELDED` or `TPM_RC_TESTING` is checked
  at the trace level (the same bytes sent again, at most 8 sends; the store's programs are checked on the commands
  that took effect); the typed error after the last resend is covered by unit tests, not by the TPM model.
- The TLC models are bounded as listed (the Lean theorems are not); the trace checks cover the recorded runs only.
- The proofs of `vinc-core` are being written. Until they are here, that crate is tested, not proven.
  This includes the half-open cap and the table of first-flight fragments held until their start arrives (at most 4
  datagrams of at most 1500 bytes per endpoint, for at most 1 s, given only to the session the start of the same
  message from the same address creates).
- `vinc-reconcile`: the refinement of the byte-level handlers to the abstract part system is proved for the split,
  the leaf rule and the frame, keep and round bounds, not end to end (that link rests on TLC and the traces); the bytes
  and rounds cost bounds are checked by TLC only; that no stale state survives across attempts is checked by TLC and
  the traces only. TLC replays a size-bounded subset of the reconcile trace; the Lean replay takes all of it.
- `vinc-broadcast`: two properties are checked by TLC and not yet proved in Lean (after a timer no expired id or log
  entry remains; an id evicted from the log stays in the dedupe set, which holds when the dedupe capacity is at least
  twice the log's, as the real constants are); the liveness theorems cover runs without restarts.
- Of the transport (`vinc-transport`) the key layer, the stream table's receive and credit path, loss recovery
  (the sent ring, the byte accounts, loss detection, the probe timer, ghosts, tail repair), the received packet ranges
  and ack thinning, connection ids, congestion control and pacing, the packet number truncation and expansion, the
  handshake fragment reassembly and the path MTU state machine are proved and traced. Not done yet: the frame codecs,
  the long and short header codecs and header protection (their lengths and errors are tested, not modelled), paths
  and migration (validation, the move to a new path, `path_lost`, the relay fallback after three timeouts), the
  timers and the closing state (every deadline, the idle timeout, draining and closing), and the two-endpoint
  scenario models. The last three act on the whole `Connection`: a trace of them needs a view of the connection
  (its paths, timers, phase and streams) and a scripted pair of connections, which this round did not build; the
  frame and header codecs need a model of every frame type and of the strict parser's errors.
  Not modelled either: the buffer of packets that arrive before their keys (at most 8 per connection, 0-RTT packets
  ahead of the Hello on a server and 1-RTT packets ahead of the message that establishes the session on either side,
  processed once it is established).
- The congestion controller's cubic term (the origin `K` and the target) is checked at full width by the Lean replay
  only; TLC checks the bounded step of congestion avoidance (see the row above). The handshake fragment theorems
  prove that a message is handed over only when covered and that the runs are exact; that every complete set of
  fragments is handed over is checked by TLC and the trace, not proved in Lean.
- The loss recovery TLC configs are small (a ring of 2 or 3 slots, three or four packet numbers, at most four to six
  calls, a clock of 8 to 90 units with the millisecond as 1 unit) and the trace check runs the real constants; the
